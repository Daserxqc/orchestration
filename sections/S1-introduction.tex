\section{引言}

函数级代码生成在部署侧首先受 API 预算约束：调用次数、上下文长度与 token 费用共同决定了测试时计算的上限\cite{chen2021evaluating,austin2021program}。在这一约束下，系统要回答的核心问题不是“模型能否偶尔写出可运行程序”，而是\textbf{如何把有限预算分配到更可能产生边际收益的环节}\cite{li2022alphacode,chen2024selfdebug,shinn2023reflexion,gou2024critic,li2025sstar}。对强模型而言，大量样本已可被\textbf{单次生成}覆盖；编排的价值在于把剩余预算投向失败形态更混杂、更需要修补或候选扩展的样本段。

本文用\textbf{预算分档编排}来刻画这一问题：在\textbf{同一实现}中，用统一入口把策略形态固定为四个可解释的预算档位，形成\textbf{从单步到级联}的递进链条——轻量单步、单步失败修补、难度分流下的重链与失败救援、以及高预算级联扩展。这样写的目的，是把比较从「模式 A 对模式 B」的松散对照，收紧为「\textbf{同一实现下逐级解锁不同计算投向}」的阶梯式对照，并自然引出后文对调用与 token 的解释需求。

失败样本并非同质：有的失败更适合用紧凑执行反馈做局部修补，有的失败则需要更广的候选探索与筛选；也可能出现「继续追加阶段但边际收益不足」的情形。由此，「多阶段」并不天然等于「更好」\cite{li2022alphacode,li2025sstar}。预算分档编排的意义，正在于让读者能够追问：\textbf{每一档多花的 token 究竟买到了哪一类能力}，而不是把复杂度本身误认为贡献。

本文正是在这一背景下展开：不把难度路由、失败修补与级联扩展写成彼此割裂的技巧清单，而把它们写成同一阶梯上的\textbf{预算形态递进}——中档强调「该不该进重链」与「失败信息如何回注」，高档强调「候选集如何扩展与组织」。本文希望说明的是，代码生成系统的提升不只来自「算得更多」，更来自\textbf{算得更对症}。

本文的贡献按“\textbf{一条主线 + 三层机制证据}”组织。主线贡献是：在单一实现与统一统计口径下给出可复现的预算分档协议，并在双基准上系统呈现\textbf{通过率--调用次数--token}前沿与部署可用的 $\rho$ 指标。机制证据包括：其一，用结构难度分与阈值 $\tau$ 形成可解释的 easy/hard 预算分配先验，并说明静态子分\textbf{并不等价于}运行失败预测器；其二，给出\textbf{multiset 随机路由}整卷对照，用于分离 hard 覆盖率与结构对齐的贡献；其三，给出失败反馈回注形态的多种子对照，刻画压缩回注相对完整 traceback 的精度与 token 差异。

\textbf{论证结构。}全文按“协议设计 $\rightarrow$ 机制验证 $\rightarrow$ 成本前沿”展开：第 3 节给出四档编排协议与设计动机；第 4 节先报告双基准端到端结果，再用控制消融验证关键机制，最后系统呈现经验收益率 $\rho$ 与部署可用的成本收益前沿；第 5 节给出讨论与结论。

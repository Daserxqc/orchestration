\begin{abstract}
在 API 计费与上下文长度约束下，函数级代码生成的部署效果取决于测试时计算如何组织，而非单次生成本身。本文将问题表述为可复现的\textbf{预算分档编排协议}：在单一实现与统一统计口径下，把从单步到级联的行为固定为四个可对照档位，使不同预算形态可在同一执行器与同一评测口径下比较。

主实验在 HumanEval 164 与 MBPP sanitized 427 上联合报告通过率、调用次数与总 token，并给出经验收益率 $\rho$。以三 seed 均值的 MBPP 为例，相对上一档的边际 $\rho$ 在单步到单步+修补档约为 $1.52$ 百分点每万 token，分流+重链与救援档约为 $0.24$，级联档约为 $0.31$；相对单步档的累计 $\rho^{\mathrm{cum}}$ 至级联档约为 $0.44$ 百分点每万 token。机制上，LR+CV 在静态子分上未学到稳定的失败预测，说明结构分更适合作为\textbf{预算分配先验}而非运行失败分类器；并在双基准上给出\textbf{multiset 随机路由}整卷对照（与同批 structural 相同的 easy/hard 个数，固定 seed 下随机置换标签，见表~\ref{tab:route_random_multiset}）。五 seed 的反馈回注形态对照显示 compressed 与 raw traceback 的均值通过率差异约 $0.096$ 个百分点、落在各自标准差量级内，而 compressed 的平均总 token 更低。

部署上，中预算侧重结构化主链与失败回注修补，高预算侧重 \texttt{extra} 候选扩展并在可选 refine 上做精度与 token 的折中。
\end{abstract}

\section{引言}

函数级代码生成在部署侧首先受 API 预算约束：调用次数、上下文长度与 token 费用共同决定了测试时计算的上限\cite{chen2021evaluating,austin2021program}。在这一约束下，系统要回答的核心问题不是“模型能否偶尔写出可运行程序”，而是\textbf{如何把有限预算分配到更可能产生边际收益的环节}\cite{li2022alphacode,chen2024selfdebug,shinn2023reflexion,gou2024critic,li2025sstar}。对强模型而言，大量样本已可被\textbf{单次生成}覆盖；编排的价值在于把剩余预算投向失败形态更混杂、更需要修补或候选扩展的样本段。

本文用\textbf{预算分档编排}来刻画这一问题：在\textbf{同一实现}中，用统一入口把策略形态固定为四个可解释的预算档位，形成\textbf{从单步到级联}的递进链条——轻量单步、单步失败修补、难度分流下的重链与失败救援、以及高预算级联扩展。这样写的目的，是把比较从「模式 A 对模式 B」的松散对照，收紧为「\textbf{同一实现下逐级解锁不同计算投向}」的阶梯式对照，并自然引出后文对调用与 token 的解释需求。

失败样本并非同质：有的失败更适合用紧凑执行反馈做局部修补，有的失败则需要更广的候选探索与筛选；也可能出现「继续追加阶段但边际收益不足」的情形。由此，「多阶段」并不天然等于「更好」\cite{li2022alphacode,li2025sstar}。预算分档编排的意义，正在于让读者能够追问：\textbf{每一档多花的 token 究竟买到了哪一类能力}，而不是把复杂度本身误认为贡献。

本文正是在这一背景下展开：不把难度路由、失败修补与级联扩展写成彼此割裂的技巧清单，而把它们写成同一阶梯上的\textbf{预算形态递进}——中档强调「该不该进重链」与「失败信息如何回注」，高档强调「候选集如何扩展与组织」。本文希望说明的是，代码生成系统的提升不只来自「算得更多」，更来自\textbf{算得更对症}。

本文的贡献按“\textbf{一条主线 + 两个机制证据}”组织。主线贡献是：在单一实现与统一统计口径下给出可复现的预算分档协议，并在 HumanEval 与 MBPP 上系统呈现\textbf{通过率--调用次数--token}前沿与部署可用的 $\rho$ 指标。机制证据按三层组织：其一，用结构难度分与阈值 $\tau$ 形成可解释的 easy/hard 预算分配先验，并以 LR+CV 说明\textbf{静态子分本身并不等价于运行失败预测器}；其二，在 HumanEval 与 MBPP 上给出\textbf{multiset 随机路由}整卷对照（固定 hard 覆盖率、打乱题—槽位对应），用于分离「覆盖率」与「结构对齐」；其三，给出失败反馈回注形态 compressed 与 raw traceback 的五 seed 对照，从均值与方差上刻画压缩回注相对完整 traceback 的精度与 token 差异。

\textbf{论证结构。}全文按“协议设计 $\rightarrow$ 机制验证 $\rightarrow$ 成本前沿”展开：第 3 节给出四档编排协议与设计动机；第 4 节先报告双基准端到端结果，再用控制消融验证关键机制，最后系统呈现经验收益率 $\rho$ 与部署可用的成本收益前沿；第 5 节给出讨论与结论。

\section{相关研究}

围绕代码生成的测试时增强，现有研究可归为三条与本文直接相关的线索。第一条是\textbf{评测与口径}：HumanEval 与 MBPP 构成函数级代码生成的主评测基线\cite{chen2021evaluating,austin2021program}，APPS、CodeXGLUE、DS-1000、EvalPlus、LiveCodeBench 等扩展了任务分布与测试覆盖\cite{hendrycks2021apps,lu2021codexglue,lai2023ds1000,liu2023evalplus,jain2024livecodebench}。第二条是\textbf{执行反馈驱动修补}：Self-Debug、Reflexion、CRITIC、Self-Refine、AgentCoder、CodeT 等工作显示，反馈是否被压缩为可执行约束，直接影响修补收益上限\cite{chen2024selfdebug,shinn2023reflexion,gou2024critic,madaan2023selfrefine,huang2024agentcoder,chen2023codet}。第三条是\textbf{测试时计算分配}：AlphaCode 及后续 test-time scaling 路线证明，候选扩展与筛选可以提升通过率，但代价是显著的 token 与调用增长\cite{li2022alphacode,li2025sstar}。

上述工作分别回答“在哪评测”“如何修补”“如何扩展计算”，但对工程部署仍有一个共同空白：当系统同时启用分流、修补与级联时，如何在\textbf{同一实现}中保证可比性，避免由模板差异、默认开关与采样口径造成的伪增益。本文据此将问题重心从“新增单模块”转为“统一协议下的预算分配”，即在统一执行器、统一统计与统一入口下，比较不同预算形态的真实边际收益。

因此，本文在相关工作中的定位是\textbf{可部署协议研究}而非单点技巧改进：主文关注成本--收益前沿，机制层关注可复现实证，最终目标是把预算决策映射为可量化的 token 代价与可执行部署建议。

\section{方法}

本文在\textbf{统一实现}（同一执行器、同一通过判定与统计口径、同一编排入口）下实现\textbf{预算分档编排}：总体形态见图~\ref{fig:overall_framework}，按题执行的端到端流水线及四档差异见第\ref{sec:overview-flow}节。其后先给出问题边界与成本记账（第\ref{sec:formal-objective}节），再分节展开难度分流、失败救援与级联等模块，用以解释各档内部的计算投向。

本文的方法设计围绕一个基本判断展开：代码生成中的额外测试时计算，只有在能够显著缩小后续搜索空间时才具有实际价值\cite{chen2024selfdebug,shinn2023reflexion,gou2024critic,li2025sstar}。因此，系统并未把预算简单地理解为「增加若干次调用」，而是将其分配到三个彼此衔接的环节中：首先判断哪些样本值得进入重路径，其次在第一次失败后提取能够约束后续生成的局部错误信息，最后在更高预算下将计算扩展到候选探索与筛选层面。如图~\ref{fig:overall_framework} 所示，本文方法的核心不在于无差别地增加阶段，而在于让不同预算档位对应不同的信息利用方式，使各档具有清晰的功能分工，而不是演化为若干边界含混的工程开关。

\subsection{总体流程与预算分档}
\label{sec:overview-flow}

对每道任务 $x_i$，系统在实现上遵循同一\textbf{外层闭环}：读入题面及（对模型可见的）测试接口信息 $\rightarrow$ 语言模型生成候选程序 $y_i$ $\rightarrow$ 在沙箱中执行单测并得到通过/失败 $\rightarrow$ \textbf{若失败}，则仅在当前\textbf{预算档位}所允许的范围内追加后续调用（修补、重链、救援或级联），直至通过或达到该档策略的上限。通过率、平均调用次数与总 token 均在同一统计管道中汇总，从而保证四档结果可比。

分档由单一入口控制：实现中将离散档位编码与仓库内模式名一一对应，避免「模式名」与「预算档位」两套开关并存带来的比较歧义。映射见表~\ref{tab:tier_mapping}；完整命令行见仓库复现说明。

各档在行为上可概括为：
\begin{itemize}
\item \textbf{单步}：一次生成即提交判定；该档不把失败样本继续送入本文后续多轮编排分支，用作轻量基线与残差起点。
\item \textbf{单步+修补}：在单次生成失败后，以执行反馈为约束进行有限轮次的修补（轻路径；对应 \texttt{single\_step\_repair} 形态）。
\item \textbf{分流+重链与救援}：先依据结构难度分数 $s_i$ 与阈值 $\tau$ 划分 easy/hard；easy 侧保持相对轻量，hard 侧进入更重主链（可含 spec/cot 等开关），并在 plus 阶段按需触发候选救援与 refine 救援；失败信息经压缩后进入 repair/replace 等闭环（见第\ref{sec:rescue}节）。
\item \textbf{级联}：在更高预算下扩展多候选生成、执行筛选与 refine；主实验采用级联默认基线，将预算集中于主级联链路（见第\ref{sec:cascade}节）。
\end{itemize}

同一外层闭环在四档下复用相同的执行与判定逻辑；各档差异主要体现在失败后的\textbf{追加调用是否发生、以何种提示形态发生、以及是否引入多候选级联}。下文第\ref{sec:formal-objective}节给出问题边界与成本记账，其后按模块说明分流、救援与级联。

\subsection{问题定义与成本记账原则}
\label{sec:formal-objective}

需要强调的是，上述编排逻辑与具体基准数据集\textbf{正交}：同一套执行器、同一套分档入口与同一统计口径同时作用于 HumanEval 与 MBPP；差异只体现在任务分布与难度天花板上，而这正是双基准并列评测的意义——观察同一编排是否在“易饱和”与“更难、更杂”的两类代码生成场景下给出一致的趋势与可解释的成本结构。

设数据集为 $\mathcal{D}=\{x_i\}_{i=1}^{N}$，其中 $x_i$ 为一道代码生成任务。系统在给定预算档位 $b$ 下生成候选 $y_i$，经执行器得到 $z_i=E(y_i)\in\{0,1\}$。本文关心的不是写出抽象的约束优化闭式解，而是\textbf{在可测的记账口径下}比较各档：对每题记录是否通过、调用次数与总 token；主文以\textbf{总 token}作为 API 成本主代理（与第~\ref{sec:cost_rho} 节 $\rho$ 一致），调用次数作为辅助指标。\textbf{单次生成}提供最低档基线，并决定后续各档所面对的\textbf{残差失败分布}——后续阶段并非替代单步，而是对残差样本做有预算上限的追加计算。

本文不在正文引入带数值权重 $\alpha,\beta$ 的联合成本泛函；若需同时按次计费与按 token 计费，可将实验中的 $\rho$ 定义改为「在固定 $\alpha/\beta$ 下的边际收益」，作为部署扩展而非本文主表默认。

\subsection{难度感知路由}
\label{sec:routing}

难度感知路由的作用，是在进入重路径之前完成一次粗粒度预算筛分。系统依据题面与测试可见结构特征，对样本进行 easy/hard 划分，使明显简单样本尽量停留在轻路径，而将更可能需要额外推理或修补的样本送入重路径。这里追求的不是完美预测器，而是避免把同等预算平均花在所有样本上。

记样本 $x_i$ 的结构难度分数为 $s_i$。实现上由 \texttt{\_difficulty\_score\_v2} 给出可分解启发式：五类子分数分别刻画题面复杂度、签名/接口复杂度、测试用例复杂度、边界条件密度与题面歧义程度；另叠加\textbf{有界体量项} $e_i$（由题面/测试长度、行数、断言行数、\texttt{candidate} 调用次数等经对数与线性缩放后相加并\textbf{上限截断}，避免总分分布漂移）。离线统计表与主程序使用同一分解，便于附录核对。
\begin{equation}
\label{eq:difficulty}
\begin{aligned}
s_i={}& p_i+\sigma_i+\tau_i+b_i+a_i + e_i,
\end{aligned}
\end{equation}
其中 $p_i,\sigma_i,\tau_i,b_i,a_i$ 分别对应题面、签名、测试、边界与歧义五类子项，$e_i$ 为体量增量。实现上，五类子分项各自在代码中经\textbf{上界裁剪}后相加得到基础分，再叠加有界体量项 $e_i$；各子项内部由若干启发式规则与\textbf{固定正权重}线性组合（例如题面长度分段、关键词命中按次加权并封顶、\texttt{assert} 行计数分段、\texttt{candidate} 形参与边界词表加权等），总分为\textbf{确定性函数}而非学习到的预测器。相对权重体现为：测试结构与边界信号在总分中通常占比较高，题面歧义与体量项起校准尺度作用；子分项与结构分档、运行标签的统计关系见附录表~\ref{tab:appendix_weight_evidence}。本文将路由解释为\textbf{预算分配规则}：用 $s_i$ 与 $\tau$ 控制 hard 覆盖率，从而在精度与 token 之间形成可调前沿（阈值消融见实验节）。

路由决策写为
\begin{equation}
r_i=\mathbb{I}(s_i\ge \tau_{\mathrm{eff}}),
\end{equation}
其中 $\tau_{\mathrm{eff}}$ 与配置中的名义结构阈值一致（当前分流+重链与救援档默认取 $1.6$）；实现仅统计分数分布（最小/中位/最大）供分析，\textbf{不对}阈值做“分布地板抬升”。$r_i=1$ 表示样本进入 hard 主链。在 \texttt{tiered} 等模式下还可叠加 LLM 评审等信号，本文主表仍聚焦于上述结构分驱动的分档端到端效果。

\textbf{Multiset 随机路由对照（实现口径）。}为分离「hard 槽位覆盖率」与「槽位与题面结构的对应关系」，仓库提供 \texttt{--difficulty\_assignment=random\_permute\_matched}：先按式~\eqref{eq:difficulty} 与 $\tau_{\mathrm{eff}}$ 得到本批任务上的 easy/hard 标签 multiset（各题 structural 判定），再在固定随机种子下对该标签序列做\textbf{均匀随机置换}，使每题被赋予 easy 或 hard 的\textbf{个数}与 structural 完全一致，但题—槽位对应被打乱；随后仍执行同一套分流+重链与救援协议。该对照\textbf{不是}「任意 token 预算下的均匀随机路由」，而是\textbf{在固定 hard 覆盖率 multiset 下检验结构对齐是否带来额外收益}，与 LR 离线证据回答的问题正交互补。

\textbf{可复现性与随机性。}随机种子固定任务顺序与部分随机模块，但生成调用仍采用非零温度，同配置重复运行可能出现个别样本通过与否或总 token 的波动；表~\ref{tab:main_results} 报告的是三 seed 的\textbf{均值与样本标准差}。部分补充表为控制算力仍为单次 seed，正文在对应表下注明。

\textbf{关于体量项与附录统计。}$e_i$ 的作用是让总分与题面、测试规模保持弱对齐，便于路由分数在不同题型下保持可解释尺度。附录中的相关性与逻辑回归结果用于描述这一结构信号与运行标签的关系；主结论仍由同协议端到端结果给出，即通过率、调用次数与 token 的联合变化。

这一阈值设定使语义保持稳定：调高阈值使更多样本停留在 easy 链，调低则更多进入 hard 链；后文阈值消融亦建立在“直接阈值、直接分流”的实现上。

\subsection{失败后救援链}
\label{sec:rescue}

难度感知只能决定哪些样本进入重路径，但并不能保证额外预算转化为有效收益。为此，本文在\textbf{分流+重链与救援}档的重路径中引入失败后救援链。其思路不是简单重试，而是将执行失败转化为后续生成可利用的局部约束\cite{chen2024selfdebug,shinn2023reflexion,gou2024critic}。系统先执行候选程序，再从运行结果中提炼与修补直接相关的错误信息，并回写到下一轮生成中。

这一设计与普通重复采样的根本区别在于，后续调用不再面对原始问题，而是面对一个已经被错误信息裁剪过的更窄搜索空间。对代码生成任务而言，第一次失败通常已经暴露出相当具体的局部结构，例如参数个数不匹配、断言不满足、边界条件处理错误，或实现主体基本正确但中间步骤存在偏差。若这些信息能够被压缩为紧凑且具有约束性的反馈，则第二次生成更可能表现为局部修补，而不是从头重写。

基于这一考虑，本文将救援链组织为“生成、执行、回写错误、再生成”的短闭环，并强调对错误信息的结构化整理，而不是直接复制全部运行日志。实现上，系统在 repair 与 replace 之间按错误类型分流：当失败形态呈现“局部可修复”特征时，如断言差异、边界条件遗漏、变量更新错误，优先走 repair；当失败形态表现为“整体方案偏离”时，如函数骨架与测试意图不匹配、核心思路错误或重复修补仍不收敛，转入 replace。该分流的目的，是把额外调用优先用于最可能产生增量的路径，避免把全局重写与局部修补混在同一提示中。

\textbf{分流机制与输入。}\texttt{repair}/\texttt{replace} 标签由\textbf{规则函数}对执行器返回的 \texttt{check\_correctness} 结果字符串做关键词判定得到（非额外模型调用）：例如未闭合字符串、\texttt{InvalidSyntax} 等归入 \texttt{replace}；缺参、参数个数不匹配、\texttt{NameError}/\texttt{IndentationError} 等可归入 \texttt{repair}；其余默认 \texttt{replace}。在 direct 与 spec 双路径都失败时，实现还比较两条路径错误标签是否一致，以决定后续修补轮数为 1 或 2（一致视为“易定位”，不一致视为“分歧、难定位”）。plus 阶段进一步提供两级救援，候选救援与 refine 救援，可分别开关。其中 \texttt{hard\_spec} 的角色是为 hard 路径提供\textbf{结构化约束提示}，即接口、边界与测试意图，使第一次重链生成先收窄解空间再进入后续救援；因此它属于主链约束模块而非后处理修饰模块。记第一次失败反馈为 $e_i^{(1)}$，压缩后的回注包为
\begin{equation}
\phi(e_i^{(1)})=\operatorname{Concat}\bigl(
\textit{错误类型},\,
\textit{截断摘要},\,
\textit{规则片段},\,
\textit{定向修补提示}
\bigr),
\end{equation}
读者可将四项理解为：归类信号、可放入提示的短错误摘要、从历史失败归纳的修补规则、以及指向具体位置的修补提示（实现中由统一格式化函数打包）。因此第二轮生成上下文可表示为
\begin{equation}
\tilde{x}_i^{(2)}=\operatorname{Concat}\bigl(x_i,\phi(e_i^{(1)})\bigr).
\end{equation}
相应地，第二轮候选程序满足
\begin{equation}
y_i^{(2)} \sim p_{\theta}\bigl(\cdot \mid \tilde{x}_i^{(2)}\bigr).
\end{equation}

这一写法强调的不是模型形式本身，而是搜索空间在执行反馈作用下发生了变化。原始 traceback 往往冗长且包含大量与修补无直接关系的细节，未经处理地回注模型容易重新放大搜索空间。该主张在表~\ref{tab:e2_feedback_format_5seed} 的 E2 对照中获得独立检验：在仅替换回注形态、其余流程不变时，\texttt{compressed} 与 \texttt{raw\_traceback} 的五 seed 均值通过率差异很小，而 \texttt{compressed} 的平均总 token 更低。因而，失败后救援的关键不在于是否追加了一次调用，而在于是否将追加预算转化为更强的局部约束。

从整体方法上看，增强版难度感知之所以应当被视作一条独立路径，正是因为它改变了额外预算的作用位置。相比于仅在题目层面继续扩展推理，失败后救援把预算进一步下沉到了错误层面的局部修补之中。这种变化虽然在流程图上只体现为少量附加步骤，但对系统搜索行为的影响是实质性的。

\subsection{高预算级联工作流}
\label{sec:cascade}

级联模块（\texttt{workflow\_cascade}）的设计目标不是继续加深单样本修补链，而是把新增计算用于\textbf{候选空间覆盖}。其架构可分为三层：\textbf{候选扩展层}（生成多候选并拉开解空间）、\textbf{执行筛选层}（在统一执行器下按测试结果过滤）、\textbf{后处理层}（仅对进入候选集的样本做有限 refine）。该设计把“生成--验证--再组织”写成显式流水线，避免把多阶段流程退化为无差别重试\cite{li2022alphacode,li2025sstar}。

实现上，级联主链按以下顺序执行：\textbf{(1) direct 基线候选}给出低成本起点；\textbf{(2) \texttt{extra} 候选扩展}在失败或低置信样本上追加候选集合；\textbf{(3) 执行筛选}按统一判定口径选择最优可行候选；\textbf{(4) refine/fuse}仅在候选池已形成可行解时触发一次性微调。该顺序的目的，是保证主要预算先用于“扩展可行解覆盖率”，而非提前消耗在后处理上。

\textbf{候选数量、可行解与 refine。}\textbf{可行解}指在给定任务上于统一执行器下通过官方单元测试的候选实现。\texttt{extra} 阶段每题最多追加的生成次数由全局上限 \texttt{max\_repair\_rounds} 与路由表共同约束：在可学习路由的自适应档位绑定中，保守/平衡/进取档分别对应最多约 1/2/3 个额外生成，并对执行器实际执行的 top-$k$ 做同档绑定（例如进取档最多执行前 3 个生成候选）；启发式路由下仍受 CLI 默认 \texttt{extra\_exec\_topk} 等下限约束，实际执行数为 $\min(\text{生成数},\text{top-}k)$。\textbf{refine\_once} 仅在开启相应 CLI 开关且路由允许时触发，用于在已形成可行候选池后对最优候选做一次微调；保守档可在路由表中关闭 refine 以省 token。

与第\ref{sec:rescue}节的失败后救援链相比，级联模块的职责边界是清晰分开的：救援链解决“已知失败样本如何被局部约束修复”，级联模块解决“在不确定解空间中如何提高命中率”。因此，级联并不是救援链的机械叠加，而是把计算投向从局部修补切换到候选覆盖与筛选组织；两者解决的是不同层级的问题。

实现上，级联模块遵循“先筛选、后精修”的触发顺序：只有候选在执行筛选后保留，才进入 refine；当候选扩展未带来有效可行解时，流程在该层停止而不继续放大后处理调用。结合实验节级联开关消融，\texttt{extra}（候选扩展）提供主增益，refine 相关开关主要负责精度--成本微调。方法上应将级联理解为“用候选覆盖换取上限”，而非对中等预算链路的逐层替代。

\subsection{预算分档与模块映射}

综合而言，\textbf{预算分档编排}将\textbf{从单步到级联}组织为四个可对照层级：\textbf{单步}提供轻量起点；\textbf{单步+修补}把计算投向可压缩的执行反馈；\textbf{分流+重链与救援}在难度分流下决定重链覆盖范围，并由失败后救援把追加调用转化为局部约束；\textbf{级联}则把计算主要投向候选扩展、执行筛选与 refine。各档差异对应的是\textbf{预算投向与信息利用方式}，而非孤立工程开关。

\section{实验}
\subsection{实验设置与协议}

主线实验在 HumanEval 164 与 MBPP sanitized 427 两条\textbf{标准函数级代码生成}基准上并行进行，用以检验\textbf{预算分档编排之统一实现}在\textbf{从单步到级联}路径上是否给出可复现、可解释的趋势：前者更贴近易饱和的短函数设定；后者提供更宽的改进空间与更可分辨的成本曲线。核心主结果模型统一为 \texttt{claude-sonnet-4-6}。预算划分为四档：单步、单步+修补、分流+重链与救援，使用 v2 打分器，以及级联；并与 \texttt{single\_step}、\texttt{single\_step\_repair}、\texttt{difficulty\_aware\_plus}（MBPP 第三档）/ \texttt{difficulty\_aware\_repair}（HumanEval 第三档）、\texttt{workflow\_cascade} 等实现模式对应，保持「预算档位=策略形态」，避免模式组合带来的解释歧义\cite{chen2021evaluating,austin2021program}。具体命令行写法见仓库复现说明。主表中 MBPP 与 HumanEval 均汇报三 seed，42、78、132，均值$\pm$样本标准差；生成阶段存在非零温度，同配置重复仍可能出现个位数样本波动，因此正文结论以区间统计与前沿形态共同解读。

\textbf{消融与主线的分工。}表~\ref{tab:main_results} 与表~\ref{tab:model_results_mbpp}、表~\ref{tab:model_results_he} 覆盖双基准、多模型的\textbf{端到端}结论；表~\ref{tab:ablation_06_threshold}--\ref{tab:ablation_08_flow} 的细粒度开关实验仅在 MBPP 上展开，用于解释\textbf{分流+重链与救援}档与\textbf{级联}档内部模块贡献与成本前沿。这样安排的首要原因是\textbf{评测动态范围}：在本文主模型设定下，HumanEval 通过率已接近饱和区间，细粒度消融更常表现为“个位数样本差异”，对模块贡献排序与阈值前沿的统计稳定性不足；MBPP 则保留更宽的改进空间，更适合承载机制解剖。其次才是 API 成本与可重复性。主结果已在 HumanEval 上验证同一编排的分档趋势，MBPP 消融进一步回答“趋势背后的机制与预算花在哪里”。

除非特别说明，MBPP 结果采用 \texttt{MBPP sanitized} 的 427 题口径，HumanEval 结果采用 164 题口径；主结果表（表~\ref{tab:main_results}）中的各方法共享同一执行脚本与同一统计方式。凡涉及外部论文结果的横向对照，均单独标注并仅作背景映衬，不参与主结论的严格同条件比较。

评价指标除了通过率之外，还同时记录平均调用次数和总 token 数。本文特别强调后两者，是因为在真实 API 场景中，调用次数并不能完整代表成本。一次很长的失败分析提示，可能比两次短调用更昂贵；而多阶段系统真正难以控制的，往往恰恰是上下文累积带来的 token 膨胀。因此，凡是涉及“方法更划算”或“预算更有效”的判断，都必须结合 token 视角来理解。就评价思想而言，这种写法与近年来关于代码生成测试时扩展的讨论是一致的，即不只比较最终正确率，也比较为获得这部分正确率所付出的额外计算\cite{li2022alphacode,li2025sstar}。

为避免“复杂流程天然占优”的偏差，本文将公平基线限定为同轮次或同预算可比形式：其一是固定采样次数的简单重试/\texttt{pass@k} 基线（即在相同候选规模下比较选择机制）\cite{chen2021evaluating}；其二是固定总 token 开销的 best-of-$N$ 基线（在相近计算预算下比较流程收益）\cite{li2025sstar}。此外，主结果采用同模型、同数据切分、同执行器与同统计口径的设置；\textbf{主表}（表~\ref{tab:main_results}）为三 seed 区间统计，多模型分档表与多数 MBPP 消融表为\textbf{单次 seed=42} 的形态扫描，二者证据权重不同（见表~\ref{tab:protocol_constraints}）。

\subsubsection{学习式路由控制基线}

为回应“结构难度分能否替代规则分流、或能否直接预测运行失败”的问题，本文在与打分表对齐的 task 级样本上给出逻辑回归 5-fold 交叉验证对照（特征含五维子分与体量项等）。结果显示：\texttt{direct\_fail} 与 \texttt{need\_reroute} 的 ROC-AUC 分别约为 0.471 与 0.473，接近随机分类器；加入扩展静态特征后 AUC 约升至 0.51，增量有限。

\textbf{正确解读。}上述结果只能说明：在当前标签口径与任务规模下，\textbf{用静态表特征去拟合“是否首轮失败/是否需要改道”这类运行标签}的判别能力弱。它\textbf{既不蕴含}“规则分流优于任意随机路由”，也\textbf{不蕴含}“规则分流优于任意学习式路由器”。其中，``规则 vs 随机''需要\textbf{协议内、可复现}的在线对照；本文在表~\ref{tab:route_random_multiset} 给出一种明确对照：\textbf{在固定 easy/hard multiset（与同批 structural 相同的 hard 覆盖率）下随机置换题—槽位对应}，再与 structural 同跑整卷。该对照仍\textbf{不覆盖}其它随机化形式（例如 Bernoulli($p$) 独立抽样导致 hard 计数方差等），故讨论中避免将结论外推为“一切随机分流均劣于结构分流”。本文将规则分流定位为\textbf{可解释、可阈值化的预算分配先验}：其有效性由端到端通过率与 token 前沿及 $\tau$ 消融共同支持，边界由 LR 证据说明“不要把同一组静态分误读为失败预测器”，并由表~\ref{tab:route_random_multiset} 说明“在固定覆盖率 multiset 下，结构对齐可带来可观测差异（且常伴随更高 token）”。

表~\ref{tab:ablation_08_flow} 表明，\texttt{extra} 所对应的候选扩展几乎是高预算性能的必要条件；一旦移除，系统迅速退化为接近单轮调用的成本结构，但通过率亦随之断崖式下降。另一方面，在默认级联基线上，refine 相关开关体现的是\textbf{精度--成本微调}而非主增益来源：关闭一次 refine 可显著节省 token，但会带来轻微降分；语义门控版本则提供折中点。需要注意，诸如“390/427 vs 392/427”这类约 2 题（同量级地，个位数题差）应按随机波动区间解读，不宜单独上升为稳定优势结论。该观察与「高预算的关键在候选扩展，次要收益来自后处理组织」一致。更一般地，这一负面结果说明“阶段更多”并不自动带来收益：当主链路已经由候选扩展覆盖主要增益后，附加后处理步骤可能只提供边际修饰，甚至在预算受限时挤占关键调用配额。

\subsubsection{证据边界与主结论的对应关系}

本文关注的是 API 成本约束下的可落地编排协议：在同等资源约束下如何组织已有能力，使通过率增益与成本增量保持可解释对应关系。

关于证据权重：分档有效性、跨模型形态与双基准趋势，应以表~\ref{tab:main_results} 的\textbf{三 seed 区间}为主证据；多模型分档表用于\textbf{单次 seed} 下的形态扫描，不宜与主表做硬数值对齐。模块主次与阈值--成本前沿，以 MBPP 上的表~\ref{tab:ablation_06_threshold}--\ref{tab:ablation_08_flow} 为机制材料（多为单次 seed）。\textbf{Multiset 随机路由}对照（表~\ref{tab:route_random_multiset}）为双基准、单次 seed 的配对整卷结果，用于补充 LR 叙述而非替代主表区间统计。

\subsection{成本--收益前沿分析}
\label{sec:cost_rho}

综合主结果与消融，可将本文系统在代码生成中的行为概括为三条可复述的观察。(1) 双基准主结果表明，从单步到级联带来的主要增量在 MBPP 上更显著，在 HumanEval 上更多体现为残差段的稳健收尾。(2) 分流+重链与救援档的阈值与流程消融表明，预算首先应花在能把搜索空间收窄的模块上（如 spec 主链），其次才是可选的推理加深与候选救援。(3) 级联档消融表明，高预算的核心不是堆叠更多阶段名称，而是候选扩展（\texttt{extra}）；在默认级联基线上，refine 相关模块主要承担精度与 token 的细粒度折中。

从工程部署角度看，可形成两级策略：在分流+重链与救援档优先通过阈值调节获得成本可控的稳定增益（推荐保留 \texttt{hard\_spec}，并按预算决定 cot 与 plus 层深度）；在级联档将 \texttt{extra} 作为不可删除模块，并在默认级联基线下按需调节 refine 强度。相较「无差别增加调用次数」，这种中预算做分流与修补、高预算做候选扩展的结构更接近可落地的 API 部署逻辑。部署前仍建议在 HumanEval 与 MBPP 两类分布上做小规模回归，以避免只优化其中一种失败形态。

最后，引入一个仅用于事后解释、而不用于训练或路由的标量。设某策略相对其前一档带来的通过率增量为 $\Delta p$，额外 token 开销为 $\Delta t$，定义经验性收益率
\begin{equation}
\rho=\frac{\Delta p}{\Delta t}.
\end{equation}
为便于横向比较，本文进一步报告“相对单步档”的累计收益率
\begin{equation}
\rho_b^{(\mathrm{cum})}=\frac{p_b-p_{\mathrm{single}}}{t_b-t_{\mathrm{single}}},
\end{equation}
并以“每万 token 带来的通过率提升百分点”呈现。表~\ref{tab:rho_frontier} 给出主结果中的对应数值。

当 $\rho$ 较高时，通常意味着新增 token 换来了更显著的正确率提升；当 $\rho$ 明显下降时，则提示系统可能进入「继续加预算但收益变缓」的区间。结合表~\ref{tab:main_results}，HumanEval 更容易出现 $\Delta p$ 较小但仍具工程意义的残差段；MBPP 则更常出现 $\Delta p$ 与 $\Delta t$ 同步变化、需要比较前沿的情形。由此，级联档更自然地扮演高预算探索上界，而分流+重链与救援档更自然地扮演中预算折中方案：二者在不同基准上的可感知幅度可能不同，但角色分工一致。

\section{讨论与结论}

本文的主结论是：在 API 成本约束下，代码生成系统的收益来自“把预算投向不同失败形态”，而不是统一增加调用次数。双基准主结果表明，同一协议下从单步到级联形成稳定前沿；中档主要提升来自分流与失败后修补，高档主要提升来自候选扩展与筛选组织。

机制证据与主结论需要分层阅读。LR+CV 在静态特征上接近随机，只能说明\textbf{离线失败标签}难以被表特征稳定预测；表~\ref{tab:route_random_multiset} 给出\textbf{固定 multiset 的整卷随机置换}对照，用于回答「在 hard 覆盖率不变时，结构—槽位对齐是否仍有边际」：MBPP 上 structural 较 random 多对 4 题但 token 更高，HumanEval 上通过率相同而 token 差较小。该对照\textbf{不}等价于所有可能随机路由；结论应限定在本文实现与单次 seed 观测内。反馈形态五 seed 对照（表~\ref{tab:e2_feedback_format_5seed}）显示均值通过率差异约 $0.096$ 个百分点且与标准差带重叠，未做 formal 检验；在此证据强度下，更稳妥的部署表述是“compressed 回注在均值上未显示精度损失，同时平均 token 更低”，而非“默认工程形态必然更优”。

对部署实践而言，可形成清晰建议：中预算优先保留 \texttt{hard\_spec} 与失败回注修补，高预算将新增计算优先分配给 \texttt{extra} 候选扩展，再按需开启 refine 微调。这一策略与第~\ref{sec:cost_rho} 节 $\rho$ 前沿一致，即在可接受 token 增量下换取更高通过率。

当前证据边界也明确：细粒度消融仍以 MBPP 为主；尽管主表中的 MBPP 与 HumanEval 均已补齐四档三 seed 区间，multiset 随机路由对照仍为\textbf{单次 seed=42}，若需与主表同级的区间统计可扩展多 seed 重复配对。跨 API 版本漂移仍待系统覆盖。后续工作将优先扩展跨 API 版本稳定性验证，并在同一函数级代码生成口径下做更长周期回归。
